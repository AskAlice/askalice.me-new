I bought a $50 "CMX X26 Ultra" — marketed as an Android 15 flagship phone. What arrived was an 11-inch MediaTek tablet running Android 10 from 2019, with its specs spoofed and a preinstalled firmware-level backdoor from the Adups FOTA family. This is the teardown: what it claims, what it actually is, the command-and-control mechanism I recovered from the firmware, and where the consumer-protection law lands.

Everything here is analysis of a device I own. Sensitive identifiers (serial, IMEI, eMMC CID, the Firebase API key) and the exact step-by-step unlock/root/cert-injection mechanics are deliberately left out of this public writeup.

The vendor image is older still — a Treble FCM level of 2 (Android 8.1) and ro.product.first_api_level=26 (Android 8.0). So an Oreo-era vendor, an Android 10 system on top, sold as "Android 15."

2. Forensic baseline

Before touching anything I took a full image of the firmware. The SoC's BootROM reported itself fully unprotected (secure-boot chain disabled), so every partition except user data could be read out and hashed into an off-device, encrypted archive — including the irreplaceable per-device partitions (nvram, nvdata, proinfo, the protected regions). That baseline made the rest of the work reversible: the device could always be restored.

3. Preinstalled-app triage

Most of what ships is ordinary MediaTek board-support bloat. Two policy oddities on a US-marketed device: RuStore (VK's Russian app store) preinstalled as a privileged system app, and Aurora Store. Neither is malware.

The real finding is com.adups.fota v5.28, baked into /system and running from first boot. It is marked PERSISTENT and PRIVILEGED, and it holds the permission set of a remote-control backdoor: RECOVERY (write OTA packages straight to the recovery partition), WRITE_SECURE_SETTINGS, REBOOT, silent READ_PRIVILEGED_PHONE_STATE, and Firebase Cloud Messaging receive. This is the same package family Kryptowire disclosed in 2016 for exfiltrating user data to China.

4. The command-and-control mechanism

The interesting part is how the C2 hid. A first pass over 21,676 extracted strings found zero references to any Adups server — no plaintext host, no encrypted blob. The reason turned out to be a neat trick: Adups builds its sensitive strings at runtime out of char[] arrays rather than storing them as string constants, so they never appear in the compiled DEX and strings/grep simply can't see them.

Writing a small decoder that walks the decompiled source and reassembles every char[] array recovered the endpoints:

  • fota5p.adups.cn — primary check-in host, in China
  • fota5p.adups.com / fruet.adups.com — region-selected counterparts
  • API base /otainter-5.0/fota5/, with fcmReport.do reporting command activity back

The control flow: the device checks in to the Adups host, commands ("orders") arrive as the data field of a Firebase push, each order is DES-decrypted with a key derived per-message, and the integer command code is dispatched. OTA payload URLs are not compiled in at all — they are delivered by the server at runtime, which is why a static scan of the APK shows nothing. The strings were obfuscated, not encrypted; once decoded, the whole mechanism is recoverable from the firmware alone.

Capability vs. observation

It's worth being precise. Proven on this device (from the permissions and the code I read): a dormant, server-commanded channel over Firebase; the ability to install OTA packages silently as system via the RECOVERY permission; and persistence that survives reboot and a normal factory reset because it lives in /system. Documented for the family (Kryptowire/BLU, 2016): timed exfiltration of SMS, contacts, call logs, IMEI and location to China. What I did not catch: this unit mid-exfiltration — the channel was never commanded while I was watching. The worst case a mechanism like this enables is total: push any payload as system on command, intercept SMS to defeat 2FA, selectively and dormant to evade detection.

5. Why the network capture looked empty

A pre-root packet capture over a proxy ran for about 70 minutes and saw nothing but benign traffic. That's not reassurance — it's the device's blind spots working as designed. The firmware forces Private DNS (DNS-over-TLS) to Google, so name lookups never hit the local resolver; the Firebase command channel is a pinned socket to Google's messaging servers that ignores a proxy; and system apps ignore any user-installed CA. Seeing the real traffic requires decrypting at the system-store level, which only becomes possible after root.

6. Unlock, root, and neutralizing it

Because the BootROM was unprotected, the bootloader could be unlocked without a wipe, and a root image inspected and reflashed from the forensic backup. (I'm omitting the exact commands here.) With root I could read the Adups app's private data, install a system-store CA via a systemless module to decrypt its TLS, and — the point of the exercise — neutralize it: the backdoor was killed and uninstalled for all users, and a systemless module blanks its /system stub so it can't respawn. A 22-package debloat followed (RuStore, a cleartext privacy tracker beaconing to heils.cn, a Verizon SIM-unlock shim, assorted MediaTek MDM and auto-start components). Of the other suspicious apps, none was a second backdoor: the "PC mode" launcher's scary permissions turned out to be over-declared and unused, and its "self-destruct" service is just a fail-open license check.

7. How far it can be rehabilitated

The system CA store is clean — 138 stock AOSP roots, no injected MITM cert, which means the TLS interception potential lives entirely in the app layer, not the trust store. The hard ceiling is the 2016 SoC and its 3.18 kernel: a device-specific LineageOS build (Android 10–12) is realistic from the matching kernel sources, but "latest Android" is not — it would need these closed MediaTek drivers ported to a far newer kernel that nobody ships. A treble GSI is the practical path to a clean, current-ish userspace.

8. Where this lands legally

Not legal advice. There are two distinct wrongs here, and the cleaner one isn't the spyware. The spec fraud — Android 10 sold as 15, a tablet sold as a phone, fabricated RAM and storage figures, a faked-forward security-patch date — is a straightforward deceptive-trade-practices claim (in Colorado, the Consumer Protection Act, with a private right of action) that needs no proof of data theft at all. The backdoor is the harder claim: capability and a named C2 host are provable, but actual interception of this user's data is not, which is exactly the standing hurdle privacy claims run into.

The closest precedent is FTC v. BLU Products (2018) — the same com.adups.fota component, collecting messages and location without consent, settled under the FTC Act. Temu's parent has already been sued by the Arkansas AG (2024) on deceptive-practices and data-harvesting theories; persuasive, not binding elsewhere, and aimed at the app rather than hardware like this. The practical routes for a device like this are regulator complaints (a state AG, the FTC, IC3) with the teardown as the evidence package — and, more valuably than any $50 refund, publishing the analysis.

Prior art

  • Kryptowire, 2016 — the original com.adups.fota disclosure (BLU R1 HD and others). CVE-2016-10136 through -10139 cover the older companion component, not this exact v5.28 variant.
  • DEF CON 26 (2018) and DEF CON 31 (2023) — Kryptowire's two "Vulnerable Out of the Box" talks on preinstalled-app vulnerabilities in cheap carrier/prepaid devices, the category this fake falls into.
  • Gamba et al., "An Analysis of Pre-installed Android Software" (IEEE S&P 2020).

On the CVE question: the backdoor, the silent-OTA channel and the spec fraud are all intentional functionality, which MITRE won't assign a CVE for. The only genuine new vulnerability I found in v5.28 is a low-severity exported content provider (CWE-862) that lets any app flip two status flags — a footnote next to everything else.
